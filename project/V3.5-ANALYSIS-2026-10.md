# servicenow-mcp-ai — 3.5 Analysis & Implementation Plan (2026-10)

Date: 2026-10-22 · Status: **proposed — docs only, no code.** Baseline: `main` at `59482af`
(3.0.0 GA on npm `latest` and the VS Code Marketplace since 2026-10-19; 100 tools in 28 packages,
default profile `discovery` = 20 tools in 4 packages; 2,635 tests pass; `tools/list` `all`
121,992 B vs the 122,112 B budget, `discovery` 23,675 B vs 23,808 B, measured with
`npm run tokens:report`).

This pass asks the question the 3.0 trackers can no longer answer: the N pillar is exhausted
([roadmap.yaml](roadmap.yaml): 149 rows, 138 done, 5 dropped, 2 open — N-11, N-33 — and 4
partial — D-6, N-4, N-51, N-53), every P row is done or dropped, and the open owner decisions
are OD-10 and OD-11. **What should the 3.1 … 3.5 minors add, and what should they optimise?**
Findings carry ids `F5-01` … `F5-54`. The implementation items they produce continue the N pillar
as `N-66` … `N-94` (plus one breaking item, `B24`, and three owner gates, `O-23` … `O-25`); they
are proposed for rows 150+ of [ROADMAP-V3.md](ROADMAP-V3.md) once the owner accepts the plan.

Evidence markers: **verified** = re-checked in code or by running a command during this pass;
**reported** = from the platform and client landscape round (web sources read on 2026-10-22,
not reproducible from the repository); **unverified** = a table, field, property or REST path
that no code reads yet — confirm it on the PDI (O-5 lineage) in the first hour of the item,
before designing.

The pass ran in five rounds the same day. Round 1 (F5-01 … F5-14) covers ServiceNow coverage:
what a developer, admin or change manager still cannot do through the server weekly. Round 2
(F5-15 … F5-22) covers the client and platform landscape: the official ServiceNow MCP Server
Console, Claude Code's tool search, the 2026-07-28 extensions, competing servers and the
distribution channels. Round 3 (F5-23 … F5-31) covers the MCP protocol and SDK surface. Round 4
(F5-32 … F5-44) covers engineering, performance and tests. Round 5 (F5-45 … F5-54) covers DX,
distribution and documentation.

## 1. Method

1. Map the shipped surface: tool names in `src/tools/*.ts`, packages in `src/mcp/registry.ts`,
   the 171 registry descriptors in `src/core/artifacts/registry-*.ts` (scripts 28, process 40,
   platform 50, ui 52, model 1), the 12 prompts in `src/mcp/prompts.ts`, the 8 skills in
   `skills/sn-*`, the REST namespaces (`grep -rhoE "/api/(now|sn_[a-z_]+)/…" src`: 12 in use).
2. For each persona (developer, admin, change manager, CMDB owner, release engineer) list the
   weekly jobs and grep `src/` for the tables and REST paths behind them. Zero hits means no
   coverage. Re-check every finding of the four audit rounds against the source before listing
   it here; two claims were corrected on the way (the registry has 2 `verified:false`
   descriptors, not 4; `RESULT_HINT_TOOLS` names 7 tools, not 8).
3. Grep for what the SDK (`@modelcontextprotocol/server` 2.3.1, `node` 2.1.1) offers and the
   server does not use: `eventStore`, `icons`, `nextCursor`, `ResourceNotFoundError`, resource
   `size` / `annotations`, `taskSupport`, `ServerEventBus`; and for the private members the
   server reaches into (`_requestHandlers`, `_registeredTools`, `isMessageIgnored`).
4. Measure: `npm run tokens:report`, `npm pack --dry-run`, `time npm test` with the junit
   reporter, `tsc --noEmit` with each candidate flag, a scratch ESLint config with
   `strictTypeChecked` + `no-deprecated`, build size with and without `removeComments`.
5. Read the landscape (official console, spec 2026-07-28 extensions, Claude Code 2.1.307 release
   notes, competing servers, channel policies) and keep only the implications that a grep over
   `src/` confirms as gaps.
6. Filter against the standing non-goals (ROADMAP-V3 "Explicitly NOT in 3.0"): no background
   scripts, no module-breadth race, no weakening of a rail, no hosted multi-tenant SaaS, no paid
   evaluation in the gate (ADR 0011).

## 3. Design principles for 3.5

1. **Rails first, still.** Every new write (F5-01, F5-04, F5-05, F5-07, F5-09, F5-11) goes through
   plan → `plan_token` → apply, is journaled per row so `revert_write` works, respects the
   existing caps and the policy, and refuses prod where the 3.0 rails refuse it. A bulk tool that
   cannot revert is not shipped.
2. **The budgets are the gate.** `tools/list` `all` has 120 B of headroom and `discovery` 133 B.
   Every item below states its byte delta; a new tool restates the budget in
   `test/output-schema.test.js` under the N-0 / O-10 procedure, and nothing new lands in the four
   default-profile packages until OD-11 is decided. Prompts and resources are not budgeted:
   prefer them where a prompt does the job (F5-12).
3. **Protocol work is client-driven.** Each protocol item names the client that benefits today
   (resumability: Claude Desktop, Cursor, VS Code over HTTP; icons and resource metadata: VS Code
   and Claude Desktop pickers; tasks: Cursor only). No feature lands for a client that does not
   consume it.
4. **Truth before volume.** Documentation items fix what is wrong before adding what is missing,
   and every corrected string gets a `docs:sync` pattern or a test so it cannot drift again.
5. **Unverified names are confirmed first.** Items carrying **unverified** paths or tables start
   with a one-hour PDI check on the connected instance and are re-sized afterwards.
6. **The engineering items keep the gate green at every step** and never touch
   `scripts/pack-check.mjs` or the ceiling (owner).
